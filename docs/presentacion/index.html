01 — Introducción

¿Qué es este proyecto?

Un sistema end-to-end que permite a agentes de seguros crear cotizaciones completas: desde datos del asegurado hasta el cálculo de prima.

  • 🎯
    No solo técnico — demostración de cómo ASDD + OpenCode construye software empresarial complejo de manera estructurada y rápida
  • 🧩
    El reto: 6 micro-flujos (MF1–MF6) que guían al agente desde la creación de cotización hasta el cálculo de prima con persistencia completa en BD
  • 🏗️
    Arquitectura: 4 microservicios (Frontend + Gateway + ms-core + ms-catalogos) sobre PostgreSQL 16
  • ⚙️
    Resultado: Folio único generado, prima neta y comercial calculadas, desglose por cobertura

05 — Arquitectura del Cálculo (MF6)

Dentro del Use Case

CalculatePremiumUseCase.execute(quoteId)
  ├── 1. Obtiene cotización + propiedades
  ├── 2. Por cada propiedad valida:
  │   ├── CP válido (5 dígitos)
  │   ├── activityCode existe
  │   └── Suma asegurada > 0
  ├── 3. Si válida → calcula:
  │   ├── sumInsured = edificio+contenidos+...
  │   ├── Por cobertura: prima = sum × tasa
  │   ├── Guarda premium_breakdowns
  │   └── netPremium = Σ primas
  ├── 4. commercialPremium = net × 1.2
  ├── 5. Transacción atómica:
  │   ├── UPDATE quotes
  │   ├── UPDATE properties
  │   └── INSERT breakdowns
  └── 6. Retorna DTO completo
// CoverageStep.tsx
const handleContinue = async () => {
  // Paso 1: Guardar
  await saveCoverages();
  // Paso 2: Calcular
  const result = await calculate();
  // Paso 3: Navegar
  navigate(`/quote/${id}/summary`, {
    state: { calculationResult: result }
  });
};
⚡ Idempotencia garantizada

Breakdowns anteriores se eliminan y recrean. Llamar POST /calculate 3 veces produce el mismo resultado.

✅ Resiliencia parcial

Inmueble incompleto → INCOMPLETE + cálculo continúa. Solo falla si TODOS son incompletos (422).

07 — Base de Datos

Esquema PostgreSQL

quotes (modificada)

  • net_premium — decimal(12,2)
  • commercial_premium — decimal(12,2)
  • commercial_factor — default 1.2
  • calculated_at — timestamp
  • version — int (optimistic lock)
  • status — DRAFT | CALCULATED

properties (modificada)

  • net_premium — decimal(12,2)
  • commercial_premium — decimal(12,2)
  • incomplete_reason — text
  • zip_code — varchar(5)
  • activity_code — varchar
  • coverage_* — decimal (5 campos)

premium_breakdowns (nueva)

  • id — uuid PK
  • quote_id — FK → quotes
  • property_id — FK → properties
  • coverage_code — varchar
  • coverage_name — varchar
  • amount — decimal(12,2)
IDX: quote_id, property_id
UNIQUE: (quote_id, property_id, coverage_code)
Flujo de migraciones: Database Agent crea migraciones primero → Backend las consume → nunca al revés. La BD es el contrato.
08 — Reglas de Negocio

Las 6 reglas que hacen funcionar el sistema

1.
Inmueble incompleto no bloquea — Si falta CP o activityCode, se marca INCOMPLETE. El cálculo continúa con los demás inmuebles válidos.
2.
Al menos uno calculable — Si TODOS los inmuebles están incompletos, retorna 422 Unprocessable Entity
3.
Versionado optimista — Cada cálculo incrementa quote.version. Conflicto de concurrencia → 409 Conflict
4.
Idempotencia — POST /calculate N veces produce el mismo resultado. Breakdowns anteriores se eliminan y recrean.
5.
Factor comercial configurable — Default 1.2, persistido en BD. Puede modificarse sin redespliegue.
6.
Tasas por cobertura — Cada cobertura tiene tasa base. Hoy en código, mañana en tabla de configuración en BD.

10 — Lecciones Aprendidas

¿Qué nos enseñó este proyecto?

✅
ASDD funciona — Spec aprobada antes de codear elimina el "scope creep" y los "¿y si hacemos...?" Ningún feature sin propósito documentado.
⚡
Paralelismo real — Backend y Frontend desde la misma spec simultáneamente redujo el tiempo de desarrollo ~40%.
🤖
OpenCode como orquestador — Agentes especializados (backend-developer, frontend-developer) producen código más limpio que un único desarrollador haciendo todo.
🗃️
La BD es el contrato — Las migraciones deben crearse PRIMERO (Database Agent), luego el backend las consume. Nunca al revés.
📋
Logs estructurados son oro — Cada log con correlación nos permitió debuggear el flujo completo end-to-end sin fricción.
